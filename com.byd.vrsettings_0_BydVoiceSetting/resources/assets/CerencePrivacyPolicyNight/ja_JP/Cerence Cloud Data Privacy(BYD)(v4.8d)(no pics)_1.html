はじめに

対象者、範囲、目的

 

Cerence Cloud Services (CCS) プラットフォームは、Cerence のマルチテナント型クラウドベースの音声認識およびインフォテインメント ソリューションです。CCS プラットフォームは、Cerence の音声認識、自然言語理解、予測テキスト、コンテンツ機能を活用して、連携しているクルマを自然なユーザー体験に変えます。CCSは、求められるサービスを提供するために、大量のトランザクションを処理することができます。

 

本書は、Cerence 指定のサードパーティー クラウドサービス プロバイダーを通じて、Cerence Cloud Servicesの導入および使用を計画している Cerence。

本書は、CCSソリューションの全体像を説明し、データ戦略に特化した内容になっています。データ戦略は、収集されるデータ、生成されるデータ、データの保存方法、およびデータ処理に関するプライバシー・セキュリティメカニズムの全体像を提供します。このホワイトペーパーでのCerenceの目標は、データフローの全体像を透明性をもって提供することです。これにより、お客様が自社のデータプライバシーポリシーを実施し、EU一般データ保護規則（GDPR）などのプライバシー規制に準拠できるようにすることです。

 

 

ドキュメント ステータス

 

本書は、Cerence のエンジニアリングおよびプロダクトマネジメントによってレビューされています。本社は、発行日現在の Cerence Cloud のアーキテクチャおよびデータプライバシーとセキュリティに関する取り組みについて説明しています。本書の更新は、新機能、技術革新、法改正、その他の要因によってもたらされる Cerence Cloud Services (CCS) ソリューションの変更を反映するために公開されます。

 

 

CCS ソリューションの概要

CCS データ フローの概要

 

CCS プラットフォームは、Vehicle Head Unit から直接、またはカスタマー ゲートウェイを介してエンドユーザーのリクエストを受信します。リクエストは Cerence ランタイム環境内で処理され（一部のケースではインフォテインメント コンテンツを取得するためにサードパーティ コンテンツ プロバイダーと連携する場合もあります）、応答が Vehicle Head Unit に返されます。

 

システムの稼働状況情報は、サービス品質と可用性の目標を達成するために、Cerence Global Operations Center（GOC）に送信されます。利用指標は、サービス管理と会計の機能をサポートするために、Cerence ビジネスインテリジェンスシステムに送信されます。処理中に生成された一部のメタデータは、オフライン分析とコア技術の継続的な改善のためにCerence ResearchGridに送信されます。

 

ドライバーが Vehicle Head Unit で音声対応アプリケーションを起動すると、ローカルの埋め込みアプリケーションが発話コマンド（例：「土曜日のアトランタの天気はどう？」）を収集し、その入力をカスタマーゲートウェイを通じてCCSランタイム環境にストリーミングします。音声コマンドの結果は車両に返され、Cerenceの埋め込みソフトウェアのローカル仲裁ロジックが、ドライバーに提供する最終結果を埋め込み音声合成ソフトウェアから導出するか、CCSプラットフォーム上の音声合成ソフトウェアから導出するかを判断します。

 

 

車両/ゲートウェイの概要

 

Vehicle Head Unit は、車内および車外で動作するアプリケーションのユーザーインターフェースを作成します。ドライバーが起動すると、顧客アプリケーションはオーディオやその他のセンサーから入力を収集し、車のコックピットで応答を処理およびレンダリングします。これらの音声コマンド要求は、安全なTLSリンクを介して顧客のゲートウェイを通じて CCS プラットフォームに送信され、リアルタイムで処理されます。

 

車両ヘッドユニット上で実行される顧客アプリケーションの主要な機能の 1 つは、顧客ゲートウェイに接続して音声処理要求を渡すときに、Globally Unique ID (GUID) を作成して渡すことです。GUID の作成は完全に顧客の管理下にあり、GUID は車両ごとに一意である必要があります。Cerence は、GUID がドライバーから切り離される可能性があることを理解しています。車両識別番号、電話番号、またはその他の形式の個人データであってはなりません。CCS の観点から見ると、この顧客が作成した GUID は「外部 ID」です。

 

Vehicle Head Unit で実行される顧客アプリケーションの 2 番目の主要機能は、テキスト データ (言語モデル登録、「LME」データ) をアップロードして音声認識のパフォーマンスを向上させる機能です。顧客アプリケーションは、ローカルのアドレス帳から連絡先名をアップロードできると想定されています。これらの名前は、リアルタイムで認識結果を統計的に偏らせ、認識パフォーマンスを向上させるために使用されます。

 

 

CCS ソリューションの概要

 

CCS ランタイム環境：CCS ランタイム環境は、エンドユーザーの要求をリアルタイムで処理します。パフォーマンス、スケーラビリティ、可用性を考慮して設計されています。CCS ランタイム環境には、Cerence サービス ゲートウェイ、Cerence 処理エンジン、および Cerence オペレーティング ツールが含まれています。

Cerence サービス ゲートウェイ：CCS ランタイム環境内で、Cerence Service Gateway は受信するエンドユーザーの要求とセッションを管理します。Cerence Service Gateway の重要な機能の 1 つは、車両ヘッドユニット上の顧客アプリケーション (およびその他の顧客アプリケーション) によって作成された「外部 ID」を「内部 ID」に変換することです。外部 ID から内部 ID へのこの変換は、ゲートウェイ内のセッションの開始時に完了する不可逆な一方向暗号化ハッシュ関数によって実行されます。外部 ID を内部 ID にハッシュすると、エンドユーザーのリクエストの処理がユーザーからさらに切り離され、その処理によって作成されたデータに外部 ID が含まれなくなります。

 

Cerence 処理エンジン：CCS ランタイム環境で、Cerence Processing Engines は、大規模な統計モデルを使用して多数の変換とアルゴリズムを適用し、ドライバーの音声コマンドを取得してテキスト翻訳に変換し、その意図を解読します。顧客アプリケーションによって提供される場合、LME データはリアルタイムの認識結果にバイアスをかけるために使用されます。この処理の結果、処理エンジンは、発話内容と処理パフォーマンス情報を含む音声データ ログを作成します。双方の合意により、LME データは記録されません。

 

Cerence 運用ツール：CCS ランタイム環境で、Cerence Operations Tools はサーバー、ネットワーク デバイスなどからインフラストラクチャ ログ (sys ログなど) を受信します。これらのログには、エンド ユーザー リクエストの処理から生じる音声発話データやその他のアプリケーション層データは含まれません。

Cerence Global Operations Center：Cerence Global Operations Center (GOC) は、CCS ランタイム環境を 24 時間 365 日監視します。CCS ランタイム環境からのパフォーマンス指標、メトリック、およびシステム健全性情報は、高いパフォーマンスと可用性レベルを確保するために GOC エンジニアに提示されます。これらのパフォーマンス指標、メトリックス、およびシステム健全性情報には、エンドユーザー要求の処理から生じる音声発話データやその他のアプリケーション層データは含まれません。

 

Cerence ビジネス インテリジェンス システム：Cerence ビジネス インテリジェンス システムは、CCS ランタイム環境から使用状況メトリックを受信して、サービス管理と会計機能をサポートします。これらのデータには音声発話は含まれません。BI の出力は、すべてのエンドユーザー リクエストの処理からのプロジェクト レイヤー メトリックを含む集計結果です。この集計結果の例には、トランザクションの数やコマンド タイプの内訳が含まれます。集計結果は各 RTE データ センターごとに生成されます。

サード パーティ コンテンツ プロバイダー：CCS は、サード パーティ コンテンツ プロバイダー（Vaisala、HERE など）と連携して、エンド ユーザーの要求に応じてインフォテインメント コンテンツを取得します。これらのサードパーティ コンテンツ プロバイダーへのクエリには音声発話データは含まれず、現在の地理的位置と、リクエストを満たすためにエンドユーザー リクエストから取得した最小限必要な情報のみが含まれます。たとえば、ドライバーが「土曜日のアトランタの天気はどうですか？」とたずねると、天気コンテンツプロバイダーへのクエリには、車の現在位置の地理情報、アトランタ市、そして曜日としての土曜日が、それぞれクエリパラメータとして含まれます。サードパーティ コンテンツ プロバイダーへのクエリにはいかなる種類のユーザー ID も含まれず、プロバイダーとの間で暗号化されたチャネル (HTTPS など) を介してクエリが実行されます。

 

Cerence Research Grid (CRG)：Cerence Research Grid は、 CCS ランタイム環境から音声データ ログを受信する。これらのデータは処理エンジンによって作成され、内部 ID、発話内容、結果の転写、解釈、および処理パフォーマンス情報を含むログで構成されます。音声データ ログはユーザー レベルで Cerence Research Grid に保存されますが、そのユーザーを直接識別するその他の情報は保持されません。

 

CCS ロギングの概要

 

CCS クラウド コンポーネントは、CLI またはクラウド ロギング インフラストラクチャと呼ばれる中央コンポーネント RTE にデータを記録します。CLI は、各音声コマンド要求 (トランザクション) のすべての情報を統合ログファイルにマージします。これらのログは Cerence Research Grid に転送され、ログの一部 (音声発話がないログなど) は BI プラットフォームに転送されます。

データ難読化プロセスは、ログ マージ プロセスの一部として CLI 内に存在します。以下のデータ プライバシー関連機能が適用されます。

·       地理位置情報は、小数点以下 1 桁まで粗く表示されるか (デフォルト)、ログから完全に抑制されます。

·       認識と解釈の結果はドメインごとにフィルタリングされます

o       たとえば、SMSメッセージ作成トランザクションでは、ログ内の音声が完全に削除され、認識および解釈の結果は抑制されます。

 

一部のフィルタリング/抑制ルールはグローバルに適用され、一部はアプリケーション固有またはデータセンター固有に適用されます。これらのルールは、各 Cerence データ センターで管理されるログ フィルタリング/抑制構成ファイルを通じて制御されます。サードパーティまたはローカルの結果が決定され、処理を完了するために車両に戻される前に、これらの結果も音声データ ログに含まれます。顧客は Cerence に連絡して、より制限的なフィルタリングとログ抑制ルールの適用をリクエストできます。これらは、トラブルシューティング、調査、ビジネス インテリジェンスに使用できる唯一のログです。

 

Cerence Cloud Services (CCS) に同意するエンドユーザー：お客様は、Cerence クラウド サービスを有効にするために、エンド ユーザーの同意を得て、エンド ユーザーに対して適切な通知を行う責任を負います。同意が完了していない場合、またはエンドユーザーが同意を撤回した場合、特定の車両に対して Cerence Cloud Services が無効になる可能性があります。CCS が無効になっている場合、すべての音声アシスタント サービスは車両内に残り、Cerence の組み込みソフトウェアによってのみ処理されます。無効にすると、埋め込まれた音声ログは CCS に送信されません。

オプトアウト/オプトイン：Cerence API を使用すると、アプリケーションはトランザクションをログ記録の「オプトイン」または「オプトアウト」として構成できます。上記の情報 (GUI 経由など) を収集し、CCS トランザクションに渡すのは車載アプリケーションの役割です。

「オプトアウト」フラグが設定されたトランザクションでは、アプリケーション ID、タイムスタンプ、サーバー使用タイミングなどの重要なフィールドを除き、ログ内のすべての情報が抑制されます。CCS が無効になっている場合、CCS によってデータが収集されないため、ログ記録の構成は無意味になります。

 

製品の改善に同意するエンドユーザー：さらに、組み込みソフトウェアは、製品の改善をオプトアウトするメカニズムとして、製品の改善フラグを FALSE に設定する機能をアップストリーム ソフトウェアに提供します。ユーザー レベルでこのフラグを FALSE に設定すると、音声データ ログが CRG に流れなくなり、このユーザーから収集された将来の音声データが次世代の音声モデルの構築やトレーニングに使用されなくなります。たとえば、GUI 開発者が製品の改善について特定の個別の同意を提供し、エンドユーザーが同意を拒否するか、この同意を撤回する場合、開発者はこのフラグを FALSE に設定してオプトアウト メカニズムを完了する必要があります。

 

 

CCS 展開アーキテクチャ

CCS ランタイム環境：

 

Cerence は現在、世界中の顧客のヘッドユニットからのリクエストを処理するために、さまざまな地域に CCS ランタイム環境を持っています。各リージョンでは、CCS ランタイム環境がパブリック クラウド環境に展開されます。ランタイム環境は、次の通りです：

·       北米

o       CCS ランタイムは、米国バージニア州に拠点を置くパブリック クラウドに導入されています2。

o       NA ランタイム環境は、ユーザーが VR 言語を米国英語、オーストラリア英語、またはシンガポール英語に設定した場合に、南北アメリカ、アジア (中国以外)、オセアニア (オーストラリアとニュージーランドを含む) からの顧客トラフィックを処理するようにプロビジョニングされます。

 

·       ヨーロッパ

o       CCS ランタイムは、オランダのアムステルダムに拠点を置くパブリック クラウドに導入されています2。

o       ヨーロッパのランタイム環境は、ヨーロッパ、アフリカ、中東からの顧客トラフィックを処理するためにプロビジョニングされています。

o       ユーザーがEUベースの言語を選択した場合、他のどの場所でも使用できます。

 

·       中国

o       CCS ランタイムは、中国の張家口と上海に拠点を置くパプリッククラウドに展開しています2。

o       中国のランタイム環境は、中国本土から発生するすべての顧客トラフィックを処理するようにプロビジョニングされています。

·       日本

o       CCSランタイムは、埼玉県に拠点を置くパブリッククラウドに導入されています2。

o       日本ランタイム環境は、マカオや香港を含む中国本土以外のアジアからの顧客トラフィックを処理するためにプロビジョニングされています。

o       ユーザーが VR 言語を中国語 (標準語) または広東語に設定した場合、他の場所でも使用できます。

2注意：Cerence は、容量計画および最適化プロセスの一環として、これらの場所を追加または変更する場合があります。Cerence は、このような予定された変更について（そのリリースの）顧客に通知します。

 

 

Cerence GOC

 

Cerence グローバル オペレーション センター (GOC) の役割は、Cerence の全世界のクラウド ホスト サービスと運用を 24 時間 365 日サポートすることです。

·       GOC はイギリスのマーローとインドのプネにあります

·       マーロー GOC は英国協定世界時午前7時から午後7時まで営業しています。

·       プネGOCは英国協定世界時午後7時から午前7時まで営業しています。

 

Cerence Research Grid

 

Cerence Research Grid (CRG) のデータは、Cerence ランタイム環境から移動されると、ランタイム形式から分離されます。CRG はこの音声データを 1 つの大きなモノリシック構造として維持していました。

顧客の指示により、音声通話ログを CRG に転送しないようにしたり、内部 UID フィールドをゼロにして音声データ ログを匿名化したりできます。

 

現在のほとんどの展開では、関連付けされていない音声ファイル（別名「発話」）の長さは通常数秒であり、匿名性がさらに高まります。同様に、発話は通常、個人データを含まない単純な指示コマンドです。データを細分化することで、十分に大きなデータ プールが作成されます。さらに、Cerence は独自の調査を実施し、上記のすべての機能が導入されている場合、音声のみから既知のデータ主体を識別することは事実上不可能であると結論付けました。

 

Cerence Research Grid は CCS ランタイム環境から音声データ ログを受信し、Cerence の研究者がさまざまな改善に利用します。Cerence Research GRID は、次のようにログをグローバルに処理します。

·       北米

o       North America Grid は、米国マサチューセッツ州サマービルにある Cerence が管理するデータ センターを拠点としています。バックアップはバージニア州の Azure US East 2 データ センターに保存されます。

·       ヨーロッパ

o       現在、ヨーロッパには研究グリッドが存在しません。すべてのランタイム ログは、北米のグリッド ロケーションに送信される前に、ヨーロッパのランタイム環境に保存されます。

·       中国

通話ログ処理：

 

CCS ランタイム環境の一部である通話ログ ストレージ システムは、複数の CCS コンポーネントからの通話ログをマージします。コンポーネントがグローバル トランザクションの一部を処理するたびに、コール ログピース が作成され、コール ログ ストレージ システムに送信されます (トランザクションの完了直後)。通話ログ保存システムは、定期的に通話ログの断片を再構成し、結合された通話ログを形成します。マージ プロセス中に、通話ログは顧客のセキュリティ ポリシーに準拠するように変更されます（例：音声を保存しない、メッセージング ドメインの ASR/NLU 結果を保存しない）。通話ログがマージされると、GRID バックエンドと BI システムで処理できるようになります。各システムは、許可されているマージされたログの部分を定期的に個別に取得します。

 

ビジネス インテリジェンス (BI)

 

Cerence ビジネス インテリジェンス システムは、CCS ランタイム環境から使用状況メトリックを受信して、サービス管理と会計機能をサポートします。これらのデータには音声発話データは含まれず、エンドユーザーのリクエストの処理から得られるアプリケーション層のメトリックのみが含まれます（例：EU データセンターでの顧客トランザクション数）。BI に送信される個人データは、ASR 結果 (顧客レポートの上位 10 件の使用統計を追跡するため)、内部 ID（固有のユーザーと全体的なトラフィックの使用状況を追跡するため）、および NLU ドメイン（顧客レポートの使用状況の種類を追跡するため）のみです。

 

すべてのランタイム環境は、Azure US East 2 リージョンの同じ中央 BI システムと統合されます。ビジネス インテリジェンス システムは、Azure US East 2 リージョンでホストされています。データは次の目的で BI システムに送信されます。

 

·       監視、分析、SLA の順守、課金、使用状況と顧客セグメンテーション、傾向の把握などに使用できる顧客向けレポートの作成。

·       生成されたレポートは、Cerence による課金、製品の改善、レイテンシ/SLA/容量分析の監視、予測などに使用できます。

·       長期間保存された要約データは、機械学習/AI アクティビティに使用して、より多くの洞察を得て、エンドユーザーに優れたエクスペリエンスを提供できます。

 

BI データフロー

 

さまざまなランタイム環境（米国、ヨーロッパなど）からのデータが CLI から抽出され、要約とレポート作成に適したモデルに変換された後、Azure の米国東部リージョンにある中央データ ウェアハウスに転送され、OLAP データ キューブに読み込まれます。レポートと分析はこれらの OLAP キューブから実行され、オプションで安全な (SSL) Web ポータルを介してアクセスされます。

 

アクセス制御

 

BI システムへのアクセスには 3 つの種類があります。

 

1.       BIポータル経由の外部顧客（顧客）（オプション）

 

BI ポータルは、顧客がそれぞれの展開に固有の集計レポートのみを表示できるように構成されています。BI ポータルにアクセスしてレポートにアクセスする前に、各ユーザー (CCS 顧客) を明示的にプロビジョニングおよび構成する必要があります。

 

2.       BI ポータルまたはポータルレポート経由の社内（Cerence）顧客

 

BI ポータルは、Cerence 社内ユーザーが洞察の収集や上記に挙げたその他の目的のために集計レポートのみを生成できるようにも構成されています。集計レポートは、顧客/顧客プロジェクトに固有、または顧客/顧客プロジェクト全体にわたって作成できます。

 

3.       開発者 / 管理者

開発者と管理者は、BI システムの開発と保守のために BI システムにアクセスする必要がある Cerence の従業員/請負業者です。これらの従業員/請負業者は、BI システムにアクセスする前に特定の権限が付与されます。BIシステムへのアクセスは、必要な場合に限られます。

 

 

グローバルオペレーションセンター（GOC）

 

GOC の役割は、Cerence の全世界のホスト サービスと運用に対して 24 時間 365 日のサポートを提供することです。そのため、サービス稼働時間の保証と確立されたサービス レベル契約の遵守を担当する高度な訓練を受けたスタッフが、1 日 24 時間、週 7 日、年間 365 日体制で常駐しています。Cerence のイベント、インシデント、問題、変更管理プロセスの実行を担当するすべてのインシデント マネージャーは、ITIL v3 Foundation 認定を受けています。GOC エンジニアは全員、Cerence の製品とサービスに対する第一線および第二線のサポートを提供するために RHCSA/RHCE のトレーニングを受けています。

GOC は、Cerence のホスト インフラストラクチャ、ネットワーク、およびアプリケーションのプロアクティブな監視を実行し、問題やイベントを報告するための主要な顧客コンタクト センターです。イベントが発生すると、GOC チケットが作成され、イベントの影響、開始時刻、解決時刻、および関連するすべてのインシデント対応とサービスを復元するためのアクションが記録されます。サービスに影響を与えるインシデント/イベント/アラートに対するインシデント対応ブリッジの調整、イベント ステータスの顧客への通知、問題解決を完了するための Tier 1 および Tier 2 の対応の調整など、さまざまなタスクを実行します。GOC はパフォーマンス KPI を追跡し、サービス パフォーマンスを定期的に報告します。社内の問題管理プロセスを推進し、繰り返し発生するサービスに影響を及ぼすインシデントを排除し、サービス品質と稼働時間の継続的な改善を推進します。GOC は、Cerence がホストするインフラストラクチャとサービスのアップグレードとメンテナンスを実行するために必要なすべての変更を調整し、指定されたメンテナンス間隔との整合性を確保します。また、セキュリティ インシデントおよびイベント管理（SIEM）プロセスによって検出されたセキュリティ関連のインシデントの調整の中心点となります。GOC は、Cerence のホストされたネットワークとインフラストラクチャへのユーザー アクセスも制御し、必要に応じて Cerence のグローバル セキュリティ ポリシーに準拠して最小限の権限アクセスを付与します。

 

GOC スタッフは現在、英国のマーローとインドのプネにいます。彼らはアクセス権を持ち、すべての地域でサービスに影響を与える問題を監視および介入して修正することができます。GOC スタッフは、問題を解決するためにさらに詳細なトラブルシューティングが必要な場合、オンコールのポケベル ローテーションを通じて追加の第 2 および第 3 ライン サポート エンジニアにアクセスすることもできます。オンコールスタッフは、ヨーロッパ、アメリカ、アジアなど世界中に配置されています。

 

GOC の拠点は、デュアル ISP ネットワーク接続によって Cerence の全世界のネットワークに接続されており、サービスと運用を維持するために必要な接続が確保されています。

GOC によって消費されるデータには個人データは含まれません。操作を監視および維持するために GOC に流れるデータにはいくつかのクラスがあります。これらには、インフラストラクチャ ログ、メトリック データ、合成トランザクション データ、監視データが含まれます。これらのデータセットには個人データは許可されません。

·       Infrastructure Logs は、システム ログ、コンテナ ログ、アプリケーション ログで構成されます。これらのログは、アプリケーションをホストする物理資産と仮想資産に関連する情報を提供します。

·       Metrics Data は、ネットワークデータ（送受信、エラー率）、ディスクデータ（使用状況、読み取り/書き込み速度、

エラー、レイテンシ）、CPU データ（使用量）、メモリ データ（使用量）から構成されます。

·       Synthetic Transaction Data は、テスト入力を使用してクライアント トランザクションをエミュレートし、トランザクション処理が成功したことを確認します。

·       Monitoring Data は、ログ、メトリック、合成トランザクション データから集計および相関され、アラートまたはイベントとメトリックを表示するダッシュボードの形式で GOC に表示されます。

 

GOC は集約された BI 情報（非個人情報）にアクセスできますが、Cerence Research Grid のデータにはアクセスできません。

·       機械学習/AI モデリングのために長期間保存されたデータを活用することで、より深い洞察を得て、エンドユーザーに優れたエクスペリエンスを提供します。

Cerence Research Grid

 

Cerence Research GridCerence Research Grid は、CCS ランタイム環境から音声データ ログを受信します。これらのデータは処理エンジンによって作成され、仮名化された内部 ID、発話、音声の結果のテキスト転写、ユーザー要求の解釈 (意図)、および処理パフォーマンス情報を含むログで構成されます。この音声データ ログは、Cerence Research Grid に保存されるため、「関連付けられていないデータ」と見なされます。つまり、データが単一のユーザーからのものであることはわかっていますが、そのユーザーを直接識別する情報はわかりません。

 

音響 / 言語 / NLU モデルの更新：音響モデルは、「cat」の「a」がどのように発音されるかなど、単語内で音がどのように表現されるかをエンコードします。言語モデルは、単語がどのように組み合わされて意味のあるフレーズになるかをエンコードします。音声認識ソフトウェアは、これら 2 種類のモデルと辞書やその他の入力を使用して、最も可能性の高い発言のシーケンスを出力します。

Cerence Research Grid 内では、生の音声データが集約され、ランタイム環境で Cerence Processing Engines を動かす統計的な音響、言語、および NLU モデルの構築に使用されます。このようなモデルは、数百から数千時間の音声と、数百万から数十億語のテキスト データ（実際のユーザーが実際に発した音声を書き起こしたもの）に基づいてトレーニングされます。

 

話者非依存言語モデルの適応：Cerence Research Grid では、話者非依存言語モデル適応 （SI-LMA）プロセスにより、市場固有の用語や新しいトレンド用語の認識が向上します。バグや誤認識を修正するためにも使用されます。

 

話者依存音響モデルの適応：Cerence Research Grid では、エンドユーザーの発話からの音声を使用して、システムを頻繁に使用するユーザーの統計と認識を最適化する音響モデルの適応を構築します。この最適化プロセスは、話者依存音響モデル適応 (SD-AMA) と呼ばれます。

 

Cerence は、統計的音響、言語、NLU モデリングにディープラーニング テクノロジーを使用します。このテクノロジーはデータ駆動型であり、より多くのデータを使用することでより優れたモデルを生成することができます。研究および工場モデルのトレーニング プロセスですべての顧客からのデータをまとめてプールすると、顧客固有のモデルに顧客データを使用するよりも高い精度を実現できます。

すべてのユーザーは、独自のデータを使用した話者依存の適応により、さらなる精度の向上が得られます。さらに、各アプリケーションでは、ユーザーの意図の表現方法（画面チュートリアル、コマーシャル、マニュアル、所有者の人口統計、以前の音声システムに対する習熟度など）が異なり、音響条件の分布も異なります。話者に依存しない適応とモデリングを介して顧客固有のアプリケーション シナリオに顧客データを使用することによる改善も、顧客のドライバーにとって独自のものです。

 

 

データ アクセス

 

Cerence Research Grid に保存されるデータは、企業レベルで管理されるグループ権限によって保護されます。そのデータへのアクセスは、最小権限モデルに基づいて必要に応じてのみ可能になります。つまり、関連する製品を作成または改善するために特定のデータを使用する必要がある研究者だけがそのデータにアクセスできるようになります。このようなアクセスは、研究者がすべての必要なデータ プライバシーとセキュリティのトレーニングを最新の状態であることを確認した後、マネージャーの要求に応じてのみ許可されます。一度許可されると、アクセスは二次認証を通じて承認された個人のみに許可されます。アクセスは研究者の職務が変わるたびに更新または取り消され、通常は 2 年ごとに見直されます。データ プライバシーとセキュリティのコースは毎年受講する必要があります。

 

Cerence Research Group には、言語に特化した言語学者の専門家だけでなく、言語に依存しないより一般的なシステムの専門家やディープラーニングの専門家もいます。彼らは協力して、顧客に可能な限り最高のソリューションとサービスを提供します。

グローバル組織および市場リーダーとして、当社は世界最高のシステムおよびディープラーニングの専門家を採用していますが、1か所に集中しているわけではありません。これらの専門家が協力して取り組むことで、トラブルシューティングが迅速化され、SLA 要件を満たす能力が向上します。

 

 

Cerence データ保持

 

Cerence ランタイム環境 / グローバル オペレーション センター

 

Cerence ランタイム環境内の音声データ ログは、デバッグおよびトラブルシューティング アクティビティをサポートするために最大 28 日間保持されます。これらの音声データ ログは、音響、言語、および NLU モデリング アクティビティをサポートするために Research Grid に送信され、エンド ユーザーの要求の処理から生じる音声発話データが含まれます。音声データ ログは、28 日後に Cerence ランタイム環境から期限切れとなり、削除されます。

 

顧客アプリケーションによって提供され、Cerence ランタイム環境で維持される言語モデル登録（LME）データは、ユーザーが 6 か月間非アクティブになると削除されます。

Cerence ランタイム環境内のインフラストラクチャ ログは、監査の目的で必要に応じて 90 日間以上保持されます。これらのパフォーマンス指標、メトリック、およびシステム健全性情報には、エンドユーザー要求の処理から生じる音声発話データやその他のアプリケーション層データは含まれません。これらのログには、エンドユーザーのリクエストの処理から生じる音声発話データやその他のアプリケーション層データは含まれません。

 

 

Cerence Business Intelligenceシステム

 

CCS ランタイム環境から Cerence ビジネス インテリジェンス システムに送信された使用状況データは、2 四半期分の集計レポートを即座に作成できるよう、6 ～ 7 か月間保持されます。Business Intelligence システムによって生成された集計データ レポートは 13 か月間保持されますが、さらに 2 年間バックアップ/アーカイブされます。

 

 

Cerence Research Grid

 

Cerence は、3 年間の保持期間も継続的に導入しており、このデータ保持規格により、データの有効期間の終了時にデータを削除することで、さらにデータを保護します。Cerence は、将来のテクノロジーで可能になったとしても、関連付けが解除された音声データを「再関連付け」しないというポリシー、制御、および顧客コミットメントを維持します。Cerence は、データ処理者としての義務を認識しており、収集された目的以外でデータを使用しないことを保証します。

 

CRG 上のエンドユーザー データ（オーディオとログ）は、「vault」と呼ばれるディレクトリとファイル システムのコレクション内で、集中型データ チームによって管理されます。通常、Vault データは大きな .zip ファイルに保存され、これらの zip ファイルのインデックスはデータベースに保持されます。ボールト ファイルのバックアップはデータ チームによって実行されます。Zip ファイルはコンテナー内のオブジェクトとしてアーカイブされます。研究者がボールト ファイルからオーディオやログのコピーを作成することは禁止されているため、データ セットは通常、ボールト内のデータへのポインターのコレクションにすぎません。これにより、データ チームは、個々のユーザー (「内部 ID」で識別) や個々のアプリケーションのデータを削除する要求に応じることができます。削除は、ボールトおよびボールト ファイルのバックアップに反映されます。

 

場合によっては、多くのユーザーからのデータが、特定の話者の発話にリンクされずに結合される場合があります。そのデータに関連付けられた「内部 ID」も削除されるため、集約されたデータはさらに完全に匿名化されます内容は次のとおりです：

 

•                      オーディオ ファイルから派生した特徴ベクトル。

•                      識別情報（電話番号など）を難読化した上で、多数のユーザーから結合されたテキスト。

•                      複数のユーザーに共通する注釈付きのインテント。

 

集約されたデータを保持することで、Cerence は音声モデルを作成し、サポートできるようになります。音響モデルのトレーニングでは、「ボールト」内の元の音声データが依然として必要になる場合がありますが、コピーは作成されず、アクセスは常にボールトを介して行われます。CRG 上のユーザー データには、研究者のラップトップ/ワークステーションからのターミナル、リモート デスクトップ、またはブラウザー アクセスを介して Research Grid からのみアクセスできます。CRG への接続は常に Cerence の VPN 内で行われます。研究者のラップトップ/ワークステーションへのデータのコピーは制限されています。

 

 

データ保持期間の短縮による影響

 

当社のディープラーニング ファクトリーのモデル トレーニング、適応プロセス、話者依存の適応プロセスはいずれも 3 年間のデータを有効に活用できます。保持期間を 3 年未満に短縮すると、フィールド データの調査による精度向上の可能性が制限されます。特定のアプリケーションからのトレーニング データは、他のアプリケーションと比較してそのアプリケーションのパフォーマンスを不釣り合いに向上させるため、工場モデルは顧客アプリケーションに対して特に最適ではない可能性があります。

さらに、顧客ドライバーに対する適応のための話者依存データの量が大幅に減ります。システムを長期間使用しないと、ドライバーによってはパフォーマンスの低下が見られる可能性もあります。最後に、研究者が実験に使用したり、長期にわたってパフォーマンスのベースライン設定に役立てたりできるようになるまでに、データの転記と注釈付けには相当な処理時間とコストがかかります。このデータを維持するために12年間の長い保持期間が設けられています。この特別なデータ セットは、収集されたすべての顧客データの一部（1% 未満）を構成します。

プライバシー管理

 

Cerence は、ビジネス ユニット内のマトリックス構造によってサポートされ、データ所有者と法務部門によって管理されるプライバシー プログラムを確立しました。Cerence は、データの使用方法とセキュリティ保護方法について、お客様に対してオープンで透明性のある対応に努めています。そのため、Cerence はオンライン プライバシー ポリシーを策定し、仮名化された個人データであっても最大 3 年間の保存期間を設定しました。Cerence は、従業員による標準的なデータ アクセスと使用方法、物理的なアクセス制御、二次認証とアクセス要件、監査証跡、ログ記録、監視に関するポリシーと手順など、管理上のデータ保護とセキュリティ対策も実装しています。情報保護とデータ セキュリティを網羅したグローバル従業員トレーニングが毎年提供され、必要に応じて追加のアドホック トレーニングとコミュニケーションが補完されます。
