Introduction

 

Audience, Scope, and Purpose

 

This document is for Cerence automotive customers who plan to deploy and use Cerence Cloud Services in and through Cerence designated third-party, cloud service providers, and agree to transfer speech data logs from CCS Runtime Environment to Cerence Research Grid (CRG).

 

This document provides an overview of the CCS solution with a focus on the User Experience Improvement Program within the solution. Data Strategy provides a comprehensive view of the data that is sent, how the data is stored and the privacy / security mechanisms surrounding the data processing in the CRG. Cerence’s goal with this whitepaper is to provide a holistic view of data flow so that vehicle drivers and passengers understand how their personal data is being used. 

 

 

Document Status

This document has been reviewed by Cerence Engineering and Product Management. It describes the Cerence Cloud architecture and practices related to data privacy and security on the date of publication. Updates to the document will be published to reflect changes in the Cerence Cloud solution, which are driven by new features, technology innovations, legislative changes, and other factors.


 

Product improvement plan overview

 

Data Flow Overview

The CCS platform receives end-user requests from Vehicle Head Units directly. The request is processed within the Cerence Runtime Environment (in some cases while interacting with Third Party Content Providers to retrieve infotainment content), and a response is returned to the Vehicle Head Unit.

Some meta data generated during processing is delivered to the Cerence Research Grid for offline analysis and continuous improvement of the core technology.


 

FAQ for User Experience Improvement Program

 

1: In what situations will data be transferred to the Cerence Research Grid (CRG)?

When a vehicle driver or passenger invokes a speech-enabled application on the Vehicle Head Unit, the application will collect a spoken command (e.g., ‘Close window’, or ‘How's the weather in Atlanta on Saturday?’) and stream that input to the CCS Runtime Environment. If the end user has consented to the use of their voice command and responses (“voice transactions”), then the data is eligible to be transferred to the CRG. Generally, only once within a 24-hour timeframe (daily) will all eligible voice transactions be transferred to the Cerence Research Grid (CRG).

 

2: Where is the Cerence Research Grid (CRG)?

The Cerence Research Grid (CRG) is based out of a Cerence-managed data center located in Somerville, MA, USA. Backups are stored in an Azure US East 2 data center in Virginia.  Cerence also uses MS Azure to provide additional processing capabilities for the Cerence-managed data center.  

 

NOTE: Cerence may change these locations as part of capacity planning and optimization processes. Cerence will inform customers (that have launched) of any such planned changes.

 

3: How is the voice data used by the Cerence Research Grid (CRG)?

Within the Cerence Research Grid raw speech data is aggregated and used to build statistical acoustic, language, and NLU models that power the processing engines in the CCS Runtime Environment.  Such data are trained on thousands of hours of speech – only a fraction of which come from vehicles – and billions of words of text data (previously and continually transcribed audio).  

 

Additionally researchers may use the data to perform error analysis across failed calls (systemic troubleshooting).

 

4: What methods apply for the data processing before the transfer to Cerence Research Grid (CRG)?

The CCS cloud components log data to a central component called Cloud Logging Infrastructure (CLI) which merges all information into a unified log file for each transaction. These logs are transferred to the Cerence Research Grid daily.

6: How frequent will the voice call logs be transferred to the Cerence Research Grid (CRG)?

The call logging storage infrastructure (CLI) storage system that is part of the CCS runtime environment merges the call logs from multiple CCS components.

Each time a component is processing part of a global transaction, a call log piece is created and sent to the CLI immediately after that transaction is completed.

The CLI reassembles the call log pieces to form a merged call log so that it can include both the voice command and response elements. During the merging process, call logs are modified to comply with customer security policies (e.g. do not keep audio and ASR/NLU results for messaging domain).

 

When a call log has been merged, it becomes available for processing by the GRID backend. The backend pulls to the GRID are performed daily (once a day).

 

 

7: How long is the data stored in Cerence Research Grid (CRG)?

Cerence has deployed the 3-year retention on a rolling basis and this data retention standard further protects the data by removing data at the end of its useful life cycle. Cerence maintains policies, controls, and customer commitments not to “re-associate” audio data, even if future technology allows it. Cerence is mindful of its obligations as a data processor and ensures that it does not make any use of the data other than for the purposes for which it was collected.

 

End-user data (audio and logs) on the CRG is managed by a centralized Data Team, in a collection of directories and file systems called the “vault”. Vault data is typically stored in large .zip files and indexes of these zip files are held in databases. Backups of the vault files are done by the Data Team. The .zip files are archived as objects in containers. It is prohibited for researchers to make copies of audio and/or logs from vault files, so data sets are generally just collections of pointers to data in the vault. This allows the Data Team to honor requests for deleting the data of individual users (identified via the “internal ID”) and/or of individual applications. The deletions taking effect on the vault and backups of the vault files.
