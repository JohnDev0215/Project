Introdução

Público, Escopo e Propósito

 

A plataforma Serviços na nuvem Cerence (CCS) é uma solução de reconhecimento de voz e de infoentretenimento da Cerence baseada na nuvem e com vários inquilinos. A plataforma CCS transforma os veículos ligados em experiências de utilizador naturais, ao tirar partido do reconhecimento de voz, da compreensão natural do idioma, do texto preditivo e das capacidades de conteúdo da Cerence. O CCS é capaz de processar grandes volumes de transações para fornecer os serviços solicitados.

 

Este documento é destinado aos clientes automotivos da Cerence que planejam implantar e utilizaros Serviços em Nuvem Cerence em e através dos provedores de serviços em nuvem de terceiros designados pela Cerence.

Este documento fornece uma visão geral da solução CCS com foco na Estratégia de Dados dentro da solução. A Estratégia de Dados oferece uma visão abrangente dos dados que são coletados, dos dados que são gerados, como os dados são armazenados e os mecanismos de privacidade/segurança em torno do processamento de dados. O objetivo da Cerence ao elaborar este documento técnico é fornecer, de forma transparente, uma visão holística do fluxo de dados, para que os nossos clientes possam implementar a respetiva política de privacidade de dados e cumprir os regulamentos sobre privacidade, como o Regulamento Geral sobre a Proteção de Dados da UE (RGPD).

 

 

Status do Documento

 

O presente documento foi revisto pelo departamento de engenharia e gestão de produtos da Cerence. Descreve a arquitetura da Nuvem Cerence e as práticas relacionadas à privacidade e segurança de dados na data de publicação. Atualizações do documento serão publicadas para refletir mudanças na solução Cerence Cloud Services (CCS), que são impulsionadas por novos recursos, inovações tecnológicas, mudanças legislativas e outros fatores.

 

 

Visão Geral da Solução CCS

Visão Geral do Fluxo de Dados CCS

 

A plataforma CCS recebe os pedidos dos utilizadores finais diretamente das Unidades Centrais do Veículo ou através de um Gateway de cliente. A solicitação é processada no ambiente de tempo de execução da Cerence (em alguns casos, durante a interação com provedores de conteúdo de terceiros para recuperar o conteúdo de info-entretenimento), e uma resposta é retornada à unidade principal do veículo.

 

Informações sobre a saúde do sistema são entregues ao Centro de Operações Globais da Cerence (GOC) para garantir os objetivos de qualidade e disponibilidade do serviço. Métricas de uso são entregues ao Sistema de Inteligência de Negócios da Cerence para apoiar as funções de gestão de serviços e contabilidade. Alguns metadados gerados durante o processamento são entregues ao ResearchGrid da Cerence para análise offline e melhoria contínua da tecnologia principal.

 

Quando um condutor executa uma aplicação com tecnologia de voz na Unidade Central do Veículo, a aplicação local integrada recolhe um comando de voz (por exemplo, "Como está o tempo em Lisboa no sábado?") e transmite esse comando através do Gateway de cliente para o Ambiente de execução CCS. Os resultados do comando de voz serão devolvidos ao veículo, onde a lógica de arbitragem local no software integrado da Cerence irá determinar se o resultado final apresentado ao condutor deve ter origem no software de síntese de voz integrado ou no software de síntese de voz localizado na plataforma CCS.

 

 

Visão Geral do Veículo/Gateway

 

A Unidade de Cabeça do Veículo cria a interface do usuário para os aplicativos que rodam dentro e fora do veículo. Após a ativação pelo motorista, os aplicativos do cliente coletam entrada de áudio e outros sensores para processamento e renderização de respostas no cockpit do carro. Estes pedidos de comando de voz são enviados através de ligação segura TLS pelo Gateway de cliente para a plataforma CCS para tratamento em tempo real.

 

Uma função chave dos aplicativos do cliente que rodam na Unidade de Cabeça do Veículo é que criam e passam um ID Globalmente Único (GUID) ao se conectar ao Gateway do cliente para passar solicitações de processamento de voz. A criação do GUID está totalmente sob o controle do cliente, e o GUID deve ser único para cada veículo. A Cerence compreende que o GUID pode ser desassociado do condutor. Não deve ser um número de identificação do veículo, número de telefone ou qualquer outra forma de dado pessoal. Do ponto de vista do CCS, esse GUID criado pelo cliente é um "ID externo".

 

Uma segunda função chave dos aplicativos do cliente que rodam na Unidade de Cabeça do Veículo é a capacidade de fazer upload de dados de texto (dados de Inscrição de Modelo de Linguagem, "LME") para melhorar o desempenho do reconhecimento de voz. É previsto que os aplicativos do cliente possam fazer upload de nomes de contato de uma agenda local. Esses nomes são usados para influenciar estatisticamente os resultados de reconhecimento em tempo real e, portanto, melhorar o desempenho do reconhecimento.

 

 

Visão Geral dos Componentes da Solução CCS

 

Ambiente de Execução CCS: O Ambiente de Execução CCS processa solicitações de usuários finais em tempo real. Foi concebido para garantir o desempenho, a escalabilidade e a disponibilidade. O ambiente de tempo de execução do CCS contém o Gateway de serviço Cerence, os mecanismos de processamento Cerence e as ferramentas operacionais Cerence.

Gateway de Serviço Cerence: Dentro do ambiente de execução CCS, o Gateway de serviço Cerence gerencia solicitações e sessões de usuários finais. Uma função chave do Gateway de Serviço Cerence é transformar "IDs externos" criados por aplicativos do cliente na Unidade de Cabeça do Veículo (e outros aplicativos do cliente) em um "ID interno". Essa transformação de ID externo para ID interno é realizada por meio de uma função de hash criptográfica irreversível unidirecional completada no início de uma sessão dentro do gateway. O hashing do identificador externo num identificador interno garante que qualquer processamento de um pedido do utilizador final é ainda mais desassociado do utilizador e quaisquer dados criados por esse processamento não contêm o identificador externo.

 

Motores de Processamento Cerence: No ambiente de tempo de execução do CCS, os mecanismos de processamento Cerence aplicam várias transformações e algoritmos usando grandes modelos estatísticos para receber o comando falado do motorista, transformando-o em uma tradução de texto e decifrando sua intenção. Se fornecidos pelos aplicativos do cliente, os dados LME são usados para influenciar os resultados de reconhecimento em tempo real. Como resultado deste processamento, os Motores de Processamento criam registros de dados de voz que contêm a fala proferida e informações de desempenho do processamento. Mediante acordo mútuo, os dados LME não serão registrados.

 

Ferramentas de Operações Cerence: No ambiente de tempo de execução do CCS, as ferramentas de operações do Cerence recebem registros de infraestrutura (por exemplo, registros de sistema) de servidores, dispositivos de rede, etc. Esses registros não contêm dados de expressão de voz ou outros dados de camada de aplicativo resultantes do processamento de solicitações do usuário final.

Centro de Operações Global Cerence: O Centro de Operações Global Cerence (GOC) monitora o Ambiente de Execução CCS 24 horas por dia, 7 dias por semana, 365 dias por ano. Indicadores de desempenho, métricas e informações sobre a saúde do sistema do Ambiente de Execução CCS são apresentados aos engenheiros do GOC para garantir altos níveis de desempenho e disponibilidade. Esses indicadores de desempenho, métricas e informações sobre a saúde do sistema não contêm dados de fala ou outros dados da camada de aplicação resultantes do processamento das solicitações dos usuários finais.

 

Sistema de Inteligência Empresarial Cerence: o Sistema de Business Intelligence Cerence recebe métricas de utilização do Ambiente de execução CCS para suportar funções de gestão de serviços e contabilidade. Esses dados não contêm fala proferida. Os resultados produzidos por BI são resultados agregados que contêm métricas do projeto do processamento de todos os pedidos do utilizador final. Exemplos desses resultados agregados incluem o número de transações e a distribuição dos tipos de comando. Os resultados agregados são gerados para cada centro de dados RTE.

Provedores de Conteúdo de Terceiros: O CCS interage com Provedores de Conteúdo de Terceiros (por exemplo, Vaisala, HERE, etc.) para recuperar conteúdo de infotainment para algumas solicitações dos usuários finais. As consultas a esses Provedores de Conteúdo de Terceiros não contêm dados de fala e contêm apenas a localização geográfica atual e as informações mínimas necessárias das solicitações dos usuários finais para atender à solicitação. Por exemplo, se um motorista perguntar: "Como está o tempo em Atlanta no sábado?", a consulta ao Provedor de Conteúdo Meteorológico conteria a localização geográfica atual do veículo, a cidade de Atlanta e o sábado como o dia, cada um como parâmetros de consulta. As consultas aos Provedores de Conteúdo de Terceiros não contêm IDs de usuários de qualquer tipo, e as consultas são realizadas por meio de um canal criptografado (por exemplo, HTTPS) para/de o provedor.

 

Grid de Pesquisa Cerence (CRG): A rede de pesquisa Cerence recebe registros de dados de fala do ambiente de tempo de execução CCS. Esses dados são criados pelos Motores de Processamento e consistem em registros que contêm o ID interno, fala proferida, transcrição resultante, interpretação e informações de desempenho do processamento. Os registros de dados de fala são armazenados na rede de pesquisa Cerence a nível de usuário, mas não retêm nenhuma outra informação diretamente identificável sobre esse usuário.

 

Visão Geral do Registro CCS:

 

Os componentes da nuvem CCS registram dados em um componente central no RTE chamado CLI ou Infraestrutura de Registro em Nuvem, que mescla todas as informações em arquivos de log unificados para cada solicitação de comando de voz (transação). Esses registros são transferidos para a rede de pesquisa Cerence, e uma parte desses logs (por exemplo, sem fala proferida) é transferida para a plataforma BI.

Um processo de ofuscação de dados reside na CLI como parte do processo de mesclagem de registros. As seguintes funções relacionadas à privacidade de dados são aplicadas:

·       As localizações geográficas são reduzidas para apenas um decimal (por padrão) ou suprimidas completamente dos logs.

·       Resultados de reconhecimento e interpretação são filtrados por domínio

o       Por exemplo, transações de composição de mensagens SMS têm o áudio nos logs completamente removido e quaisquer resultados de reconhecimento e interpretação suprimidos

 

Algumas regras de filtragem/supressão aplicam-se globalmente e outras aplicam-se com base numa aplicação ou centro de dados específico. Essas regras são controladas por meio de arquivos de configuração de filtragem/supressão de registros mantidos em cada um dos centros de dados da Cerence. Quando resultados de terceiros ou locais são determinados e antes de serem retornados ao veículo para completar o processamento, esses resultados também serão incluídos no registro de dados de fala. Os clientes podem entrar em contato com a Cerence para solicitar a aplicação de regras mais restritivas de filtragem e supressão de logs. Esses são os únicos registros disponíveis para solução de problemas, para pesquisa e para inteligência empresarial.

 

Consentimento do Usuário Final para os Serviços de Nuvem Cerence (CCS): O cliente é responsável por coletar o consentimento dos seus usuários finais e/ou fornecer o aviso apropriado para habilitar os serviços de nuvem da Cerence. Se o consentimento não for concluído ou o usuário final retirar seu consentimento, os Serviços de Nuvem Cerence podem ser desativados para um veículo específico. Quando o CCS é desativado, todos os serviços de assistente de voz permanecerão no veículo, sendo manuseados apenas pelo software embarcado da Cerence. Nenhum registro de fala embarcada será enviado para o CCS quando estiver desativado.

Opção de saída/opção de entrada: As APIs da Cerence permitem que uma aplicação configure uma transação como "opt-in" ou "opt-out" do registro. É responsabilidade da aplicação no carro coletar essa informação (por exemplo, via GUI) e passar isso na transação do CCS.

As informações no registo serão suprimidas nas transações com o sinalizador "exclusão", exceto alguns campos essenciais, como o identificador da aplicação, carimbos de data e hora, e tempos de utilização do servidor. Se o CCS for desativado, a configuração do registo é considerada irrelevante, uma vez que o CCS não recolherá quaisquer dados.

 

Consentimento do usuário final para melhorias de produto: Além disso, o software embarcado fornece ao software upstream a capacidade de definir a marca de melhoria de produto como FALSO, como um mecanismo para optar por não participar das melhorias de produto. Definir essa marca como FALSO a nível de usuário desativará os registros de dados de fala de serem enviados ao CRG, impedindo que futuras vozes coletadas desse usuário sejam usadas para construir ou treinar nossos modelos de voz de próxima geração. Portanto, por exemplo, se o desenvolvedor da GUI oferecer um consentimento específico e separado para melhorias de produto e o usuário final recusar o consentimento ou retirar esse consentimento, o desenvolvedor deve definir essa marca como FALSO para completar o mecanismo de exclusão.

 

 

Arquitetura de Implantação do CCS

Ambientes de Execução

 

A Cerence atualmente possui ambientes de execução CCS em diferentes regiões para atender às solicitações das unidades principais dos clientes globalmente. Em cada região, o ambiente de execução CCS é implantado em um ambiente de nuvem pública. Os ambientes de execução são:

·       América do Norte

o       O ambiente de execução CCS é implantado na nuvem pública com base em Virgínia, EUA2.

o       Os ambientes de execução na América do Norte são disponibilizados para gerir o tráfego de clientes das Américas, Ásia (exceto China), Oceânia (incluindo Austrália e Nova Zelândia) quando o utilizador define o idioma de RV como inglês dos EUA, inglês da Austrália ou inglês de Singapura.

 

·       Europa

o       O ambiente de execução CCS é implantado na nuvem pública com base em Amsterdã, Países Baixos2.

o       Os ambientes de execução da Europa são provisionados para lidar com o tráfego de clientes da Europa, África e Oriente Médio.

o       Qualquer outro local quando o usuário seleciona um idioma baseado na UE.

 

·       China

o       O ambiente de execução CCS é implantado na nuvem pública com base em Zhangjiakou e Xangai, China2.

o       Os ambientes de execução da China são provisionados para lidar com todo o tráfego de clientes originários da China continental.

·       Japão

o       O ambiente de execução CCS é implantado na nuvem pública com base em Saitama, Japão2.

o       O ambiente de execução do Japão é provisionado para lidar com o tráfego de clientes da Ásia, exceto a China continental, incluindo Macau e Hong Kong.

o       Qualquer outro local quando o usuário define o idioma de VR para mandarim ou cantonês.

2NOTA: A Cerence pode adicionar ou alterar esses locais como parte do processo de planejamento de capacidade e otimização. A Cerence informará os clientes (que lançarem) sobre quaisquer alterações planejadas.

 

 

Cerence GOC

 

A função do Centro de Operações Globais (GOC) da Cerence é fornecer suporte 24 horas por dia, 7 dias por semana, para as operações e os serviços hospedados em nuvem da Cerence em todo o mundo.

·       O GOC está localizado em Marlow, Reino Unido, e Pune, Índia

·       O GOC de Marlow opera das 7h às 19h, horário UTC do Reino Unido

·       O GOC de Pune opera das 19h às 7h, horário UTC do Reino Unido

 

Rede de Pesquisa Cerence

 

Os dados na rede de pesquisa Cerence (CRG) são desagregados de sua forma de tempo de execução quando os dados são movidos do ambiente de tempo de execução Cerence. O CRG mantém esses dados de fala como uma grande estrutura monolítica.

A critério do cliente, é possível impedir que os registos de chamadas de voz sejam transferidos para a GCR ou tornar anónimos os registos de dados de voz, ao colocar a zeros o campo UID interno.

 

Na maioria das implantações atuais, os arquivos de áudio desassociados, também conhecidos como "enunciados", normalmente têm poucos segundos de duração, o que contribui ainda mais para o anonimato. Da mesma forma, os enunciados são normalmente comandos diretos simples que não contêm dados pessoais. Ao desagregar os dados, são criados conjuntos de dados suficientemente grandes. Além disso, a Cerence realizou sua própria pesquisa e concluiu que, onde todos os recursos descritos acima são implantados, é virtualmente impossível identificar um sujeito de dados conhecido apenas pela voz.

 

A Grelha de pesquisa Cerence recebe registos de dados de voz do Ambiente de execução CCS, que são depois utilizados para os investigadores da Cerence levarem a cabo várias melhorias. A rede de pesquisa Cerence processa os registros globalmente da seguinte forma:

·       América do Norte

o       A rede da América do Norte está baseada em um centro de dados gerenciado pela Cerence, localizado em Somerville, MA, EUA. Os backups são armazenados em um centro de dados do Azure US East 2 na Virgínia.

·       Europa

o       Atualmente, não existe uma rede de pesquisa na Europa. Todos os registros de execução são armazenados no ambiente de execução europeu antes de serem enviados para o local do grid da América do Norte.

·       China

o       Atualmente, não existe uma rede de pesquisa na China. Todos os registros de execução são armazenados no ambiente de execução chinês para cumprir com as regulamentações locais. Os registros são anonimizados antes de serem enviados para o local da rede da América do Norte.

·       Japão

o       Atualmente, não existe uma rede de pesquisa no Japão. Todos os registros de tempo de execução são armazenados no ambiente de tempo de execução no Japão antes de serem enviados para o local da rede na América do Norte.

 

 

Sistema de Inteligência Empresarial da Cerence:

 

O sistema de inteligência de negócios Cerence recebe dados de registro de aplicativos do ambiente de tempo de execução do CCS para dar suporte às funções de gerenciamento de serviços e contabilidade. Esses dados não contêm comandos de voz e apenas contêm métricas na camada de aplicação resultantes do processamento de solicitações dos usuários finais (por exemplo, número de transações de clientes nos centros de dados da UE).

Os sistemas de Inteligência de Negócios estão atualmente hospedados no Leste de Azure US 2.

 

 

Arquitetura Detalhada dos Nós

Controlo de acesso ao Ambiente de execução CCS

Os Ambientes de execução Cerence podem ser acedidos pelas equipas de engenharia de fiabilidade do local com operações alojadas e pelas

Engenharia DevOps hospedadas pela Cerence. O Ambiente de execução Cerence está totalmente protegido por ligações baseadas em VPN e controlos de acesso baseados em políticas, integrados no Active Directory Cerence. Grupos e permissões são estabelecidos para garantir que apenas pessoas autorizadas tenham acesso a esse ambiente.

Processamento de Registro de Chamadas:

 

Sistema de armazenamento de registro de chamadas que faz parte do ambiente de execução do CCS, mescla os registros de chamadas de múltiplos componentes do CCS. Cada vez que um componente processa parte de uma transação global, um pedaço de registro de chamada é criado e enviado ao sistema de armazenamento de registros de chamadas (imediatamente após a conclusão da transação). Periodicamente, o sistema de armazenamento de registros de chamadas reagrupa os pedaços de registros de chamadas para formar um registro de chamadas mesclado. Durante o processo de mesclagem, os registros de chamadas são modificados para cumprir as políticas de segurança do cliente (por exemplo, não armazenar áudio, não armazenar resultados de ASR/NLU para o domínio de mensagens). Quando um registro de chamadas é mesclado, ele fica disponível para processamento pelo backend da Rede e pelo sistema de BI. Cada sistema puxará separadamente as partes dos registros mesclados que têm permissão de acesso em intervalos regulares.

 

Inteligência de Negócios (BI)

 

O Sistema de Inteligência de Negócios Cerence recebe dados do registro de aplicativos do Ambiente de Execução CCS para dar suporte às funções de gerenciamento de serviços e contabilidade. Esses dados não contêm dados de fala e contêm apenas métricas de camada de aplicação resultantes do processamento de solicitações de usuários finais (por exemplo, número de transações de clientes em centros de dados da UE). Os únicos dados pessoais enviados para o BI são os resultados de ASR (para rastrear as 10 principais estatísticas de uso para relatórios de clientes), o ID Interno (para rastrear usuários únicos e uso geral de tráfego) e o domínio NLU (para rastrear o tipo de uso para relatórios de clientes)

 

Todos os Ambientes de Execução integram-se com o mesmo sistema central de BI na Região Leste dos EUA 2 do Azure. O Sistema de Business Intelligence (BI) está hospedado na região Leste dos EUA 2 do Azure. Finalidades do Envio de Dados para o Sistema de BI:

 

·       Relatórios para Clientes: Monitoramento, análises, adesão a SLA, faturamento, entendimento de uso e segmentação de clientes, propensão, etc.

·       Relatórios Internos da Cerence: Faturamento, melhoria de produtos, análise de latência/SLA/capacidade, previsão, etc.

·       Aprendizado de Máquina/IA: Dados resumidos armazenados por longos períodos para obter mais insights e oferecer melhores experiências aos usuários finais.

 

Fluxo de Dados do BI:

 

Dados de vários ambientes de runtime (e.g. EUA, Europa, etc.) são extraídos do CLI, transformados em um modelo apropriado para sumarização e relatórios, transferidos para um data warehouse central na região Leste dos EUA do Azure e carregados em cubos de dados OLAP. Relatórios e análises são gerados a partir desses cubos OLAP e podem ser acessados opcionalmente através de um portal web seguro (SSL).

Rede de Pesquisa Cerence

 

Rede de Pesquisa Cerence: A Rede de Pesquisa Cerence recebe registros de dados de fala do Ambiente de Execução CCS. Esses dados são criados pelos Motores de Processamento e consistem em logs que contêm um ID interno pseudonimizado, uma expressão falada, uma transcrição textual resultante do áudio, uma interpretação (intenção) da solicitação do usuário e algumas informações de desempenho do processamento. Esse registro de dados de voz é considerado "dados desassociados" pois é armazenado na rede de pesquisa da Cerence, onde sabemos que os dados são apenas de um único usuário, mas não conhecemos nenhuma informação diretamente identificável sobre esse usuário.

 

Atualizações de Modelo Acústico/Linguagem/NLU: Um modelo acústico codifica como os sons são representados em palavras, como o som do 'a' em "gato". Um modelo de linguagem codifica como as palavras se combinam em frases que têm significado. Usando esses dois tipos de modelos, bem como dicionários e outros insumos, o software de reconhecimento de voz produzirá a sequência mais provável do que foi dito.

Dentro da rede de pesquisa da Cerence, os dados de voz brutos são agregados e usados para construir os modelos estatísticos acústicos, de linguagem e NLU que alimentam os Motores de Processamento da Cerence no Ambiente de Execução. Esses modelos são treinados em centenas a milhares de horas de fala, e milhões a bilhões de palavras de dados textuais (áudio transcrito de usuários reais dizendo coisas reais).

 

Adaptação de Modelo de Linguagem Independente de Fala: Na Grelha de pesquisa Cerence, o processo de Adaptação do modelo de linguagem de orador independente (SLI-LMA) melhora o reconhecimento de termos específicos do mercado e novos termos de tendência. Também é usado para corrigir alguns erros ou falhas de reconhecimento.

 

Adaptação de Modelo Acústico Dependente de Fala: Dentro da rede de pesquisa da Cerence, o áudio das expressões dos usuários finais é usado para construir adaptações de modelo acústico que otimizam as estatísticas e o reconhecimento para os usuários que usam o sistema frequentemente. Esse processo de otimização é chamado de Adaptação de Modelo Acústico Dependente de Fala (SD-AMA).

 

A Cerence usa tecnologia de aprendizado profundo para modelagem estatística acústica, de linguagem e NLU. A tecnologia é orientada por dados e pode produzir um modelo melhor ao usar mais dados. Agrupar dados de todos os clientes juntos em nosso processo de treinamento de modelo de pesquisa e fábrica pode alcançar melhor precisão do que usar dados de clientes para modelos específicos de clientes.

Todos os usuários obterão uma melhoria adicional de precisão com a adaptação dependente de falante usando seus próprios dados. Além disso, cada aplicativo tende a ter diferenças em como as intenções dos usuários são expressas (por exemplo, devido a tutoriais de tela, comerciais, manuais, demografia dos proprietários, familiaridade com sistemas de voz anteriores) e possuem diferentes distribuições de condições acústicas. A melhoria ao usar dados de clientes para cenários de aplicação específicos de clientes via adaptação e modelagem independente de falante também é única para os motoristas dos clientes.

Rede de Pesquisa Cerence

 

A Cerence implementou uma política de retenção de 3 anos em uma base contínua, removendo dados no final de seu ciclo de vida útil, o que protege ainda mais os dados. A Cerence aplica políticas, controlos e compromissos com os clientes no sentido de não "voltar a associar" dados de áudio desassociados, mesmo que a tecnologia permita fazê-lo no futuro. A Cerence está ciente de suas obrigações como processadora de dados e garante que não utiliza os dados além dos propósitos para os quais foram coletados.

 

Os dados dos usuários finais (áudio e registros) na CRG são gerenciados por uma equipe centralizada de dados, em uma coleção de diretórios e sistemas de arquivos chamados de "vault". Os dados do Vault são normalmente armazenados em grandes arquivos .zip e os índices desses arquivos zip são mantidos em bancos de dados. Os backups dos arquivos do Vault são feitos pela equipe de dados. Os arquivos .zip são arquivados como objetos em contêineres. É proibido que pesquisadores façam cópias de áudio e/ou registros dos arquivos do Vault, então os conjuntos de dados geralmente são apenas coleções de ponteiros para dados no Vault. Isso permite que a equipe de dados atenda a solicitações para excluir os dados de usuários individuais (identificados via o "ID interno") e/ou de aplicações individuais. As exclusões afetam o Vault e os backups dos arquivos deste.

 

Em alguns casos, os dados de muitos usuários são combinados sem vínculo com qualquer fala de um locutor específico. Como até mesmo o "ID interno" associado a esses dados é descartado, os dados agregados tornam-se ainda mais anonimizados. Podem consistir em:

 

•                      Vetores de características derivados dos arquivos de áudio.

•                      Texto combinado de muitos usuários depois que as informações de identificação (como números de telefone) são ofuscadas.

•                      Intenções anotadas comuns a vários usuários.

 

A retenção dos dados agregados permite que a Cerence crie e suporte modelos de voz. Para o treinamento de modelos acústicos, os dados de fala originais no "vault" ainda podem ser necessários, mas não são feitas cópias e o acesso é sempre feito através do vault. Os dados dos usuários na CRG são acessados apenas a partir da rede de pesquisa via terminal, desktop remoto ou acesso ao navegador do laptop/estação de trabalho do pesquisador. As conexões com a CRG são sempre feitas dentro da VPN da Cerence. As cópias dos dados para o laptop/estação de trabalho de um pesquisador são restritas.

 

 

Impactos da Redução do Período de Retenção de Dados

 

Tanto o treinamento do modelo de fábrica de aprendizado profundo quanto o processo de adaptação e o processo de adaptação dependente do locutor podem fazer uso eficaz de 3 anos de dados. Reduzir o período de retenção para menos de 3 anos limita o potencial de melhoria de precisão ao explorar dados de campo. Como os dados de treinamento de uma determinada aplicação melhoram desproporcionalmente o desempenho dessa aplicação em comparação com outras, os modelos de fábrica podem ser especificamente menos ótimos para aplicações de clientes.

Além disso, haverá uma quantidade muito menor de dados dependentes do locutor para adaptação para motoristas de clientes. É possível que alguns motoristas possam experimentar uma degradação de desempenho se não usarem o sistema por um período prolongado. Finalmente, há um tempo de processamento e custo não triviais para transcrever e anotar dados antes que possam estar disponíveis para pesquisadores para experimentação e ajudar a estabelecer a base de desempenho ao longo do tempo. Um período de retenção mais longo de 12 anos é mantido para sustentar esses dados. Este conjunto de dados especial constitui uma fração (menos de 1%) de todos os dados de clientes coletados.
